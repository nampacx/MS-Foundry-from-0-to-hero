## [0.2] – 2026-11-03

Second release: chapter 15 on the Microsoft Copilot harness with skills that run scripts, skills on demand with `SkillsProvider`, a threshold router in the workflows chapter, and a quality pass over every notebook. Merged in [nampacx/MS-Foundry-from-0-to-hero#3](https://github.com/nampacx/MS-Foundry-from-0-to-hero/pull/3), [nampacx/MS-Foundry-from-0-to-hero#4](https://github.com/nampacx/MS-Foundry-from-0-to-hero/pull/4), [nampacx/MS-Foundry-from-0-to-hero#5](https://github.com/nampacx/MS-Foundry-from-0-to-hero/pull/5), [nampacx/MS-Foundry-from-0-to-hero#6](https://github.com/nampacx/MS-Foundry-from-0-to-hero/pull/6), [nampacx/MS-Foundry-from-0-to-hero#7](https://github.com/nampacx/MS-Foundry-from-0-to-hero/pull/7).

### Added
- Notebook helper modules next to `stark_harness.py`, so the cells keep only data and calls: `stark_replies.py` (chapters 04–09: `show_reply` shows the prompt, the tool calls, the whole answer and a check table; skill and escalation checks), `stark_evals.py` (10–11: `show_scores`, `show_pass_rates` with the judge's full reasons), `stark_guardrails.py` (14), `stark_workflows.py` (16) and `stark_a2a.py` (17). `stark_helpers.py` gains `messages`, `answer_text`, `final_message` and `mark` for reading a reply, shared by all of them.
- `AGENTS.md`, "Notebook quality (the learner's view)", and the `review-notebook` skill: what chapter 15 taught about notebooks for learners (placement, one experiment per cell with goal and expected outcome, visible prompts and full answers, robust checks on model output, clear names, helpers out of cells), as rules and a checklist for the other chapters.
- `notebooks/stark_harness.py`: chapter 15's helpers (`publish_skill`, `ask_harness`, `invoice_request`, `review_invoice`, `show_ledger` and the Markdown view of each turn) live in their own module, so the chapter's cells show only the calls. The two calls the chapter teaches, `create_from_files` and the harness request, stay as snippets in its markdown.
- Chapter 15 `15_copilot_harness.ipynb` 🧪: J.A.R.V.I.S. as a prompt agent on the new Microsoft Copilot harness. It uploads the `stark-escalation` and `invoice-review` skill folders as zip packages (`create_from_files`), creates the agent with `MicrosoftCopilotHarness()` and pinned `SkillReference`s, keeps the harness shell on for the skill scripts and switches off subagents. Section 4 extracts two invoice PDFs with Document Intelligence and sends four invoices, each built to trip a different `invoice-review` script. Each case has its own cell with its goal, inputs and expected verdict, builds its prompt with `invoice_request()` in plain sight (case A opens a new conversation, so the cases can be run again), and shows each turn as Markdown: the prompt (extracted JSON folded away), the agent's full answer and a check table (verdict, scripts run, scripts missed). Names shared between cells say what they hold (`preview_project`, `sdk_conversation`, `pym_invoice`, `review_invoice()`). Section 5 shows the per-conversation workspace in three steps, each with its goal and expected outcome: the same ledger question in the old and in a new conversation (the file exists only in the old one), then case A's prompt in the new conversation, where it is approved again. Tested on a live project.
- `invoice-review` skill: five standard-library scripts the Copilot harness runs with its shell tool (`check_invoice.py`, `vendor_check.py`, `iban_check.py`, `ledger.py`, `approval_limit.py`), plus `assets/` with the vendor master, approval limits and an example invoice. `check_invoice.py` doesn't flag a low-confidence amount that the arithmetic confirms (`confirmed_by_arithmetic`), so a clean invoice whose total Document Intelligence read with low confidence is still approved. `SKILL.md` lists the exact commands, adds the vendor, IBAN and duplicate checks, and tells agents without shell (chapters 16, 17, `jarvis-hosted`) to say those checks were not run. `jarvis-skills` sees the scripts but has no script runner, so it can't run them.
- `src/jarvis-harness/azure.yaml` 🧪: the same agent as its own azd project (`azure.ai.skill` services for both skills, `azure.ai.agent` with `harness.type: microsoft_copilot_preview`), deployed into the existing STARK project with `azd deploy --all`. `scripts/harness_env.py` fills its azd environment from `.env`; `sync_skills.py` now also copies `skills/` there, without `__pycache__`. The agent keeps shell on for the skill scripts.
- [copilot-harness.md](docs/copilot-harness.md) (doc 14): what the harness changes, the four building blocks from the 2026-10-28 announcement, authoring options, request rules, skills that run scripts, workspace, azd deploy, security, limits and sandbox prices from 2026-12-01.
- [hosted-agents.md](docs/hosted-agents.md): long-running resilience for hosted agents (generally available) as a not-implemented option, and a pointer to the Copilot harness for agents that need no loop of their own.
- Chapter 07, section 6: a marker test that reads the skill from the toolbox with `resources/read` and compares an answer with and without it, to prove a toolbox skill is really used. 🧪
- Hosted agent `jarvis-skills` (`src/jarvis-skills`, new `azure.yaml` service): J.A.R.V.I.S. that loads skills on demand with Agent Framework's `SkillsProvider` (the `skills/` files plus a code-defined `workshop-status` skill) instead of pasting them into the instructions. Chapter 09 section 4 deploys it and prints which skill tools the model called; the old section 4 is now section 5. `azd deploy` without a service name now deploys it too. Tested on a live project.
- `samples/skills_provider.py`: runs the `jarvis-skills` agent as a plain script, no deploy, and prints which skill tools the model called. The fast loop for drafting a skill. Explained in [mcp-skills.md](docs/mcp-skills.md) section 4, with pointers from chapter 07, `story.md` and the glossary.
- Chapter 16, section 1: a threshold router. The extractor answers in a fixed JSON shape, and conditional edges (`Case` / `Default`) in your code send the invoice to automatic approval, the reviewer or escalation, without a model choosing the path. Explained in [workflows.md](docs/workflows.md). Not run on a live project yet.
- `CHANGELOG.md` and the rule in `AGENTS.md` that every change adds a line here.
- [troubleshooting.md](docs/troubleshooting.md) section 3: what to do when a hosted agent returns `500 internal server error`: read its container log, and restore a deleted Entra agent identity.

## [0.1] – 2026-10-15

First release: a story-driven Microsoft Foundry tutorial, from a first model call to a team of agents. Merged in [nampacx/MS-Foundry-from-0-to-hero#1](https://github.com/nampacx/MS-Foundry-from-0-to-hero/pull/1) and [nampacx/MS-Foundry-from-0-to-hero#2](https://github.com/nampacx/MS-Foundry-from-0-to-hero/pull/2).

### Added
- Infrastructure: one `azd up` deploys a Foundry resource and project with models, Application Insights, Log Analytics and role assignments (Bicep), and writes `.env`.
- Chapters 00–16 as notebooks: models and conversations, tracing, prompt agents, tools, MCP, skills 🧪, agents from YAML, hosted agents, datasets and evaluations, OCR and Document Intelligence, guardrails and red teaming 🧪, workflows, and the A2A capstone 🧪.
- Hosted agents `jarvis-hosted`, `invoice-workflow` and `morning-briefing` (`azure.ai.agent` services in `azure.yaml`). `invoice-workflow` and `morning-briefing` were deployed and called on a live project.
- The repo's own MCP server `stark-mcp` (`src/stark-mcp`), shared helpers in `notebooks/stark_helpers.py` and `notebooks/stark_docs.py`, and scripts for model checks, agent deployment, skill sync, MCP connection, role grants and teardown.
- Docs in reading order, from `concepts.md` to `capstone.md`, plus glossary, troubleshooting and portal tour, and `story.md` as one build log.

### Fixed
- `azd` and notebook failures found while running the chapters on a real project: pinned `azd` and Foundry extension versions, the Bicep outputs the `azure.ai.*` services need, embeddings on the account endpoint, front matter in `SKILL.md` on Windows (CRLF) checkouts, and notebooks that can be re-run.
